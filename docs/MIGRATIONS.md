# Migrations

Use migrations for persistent schema changes in projects built from this template.

During master startup, `init.js` runs the shared migrator with `sync: true` and then applies pending tracked migrations. The startup path is guarded so it only auto-bootstraps against the expected worktree-local DB target unless an explicit deployment override is set. The CLI commands below remain useful for manual rollout steps, debugging, and inspection.

## Canonical workflow

Create a migration:

```sh
npm run migration:new -- --name=create-users-table
```

Apply pending migrations:

```sh
npm run migrate
```

Inspect status:

```sh
npm run migrate:status
```

Rollback the latest migration:

```sh
npm run migrate:down
```

Manually mirror the startup bootstrap path against a scratch database:

```sh
npm run migrate -- --sync
```

`--sync` initializes the current model graph before pending migrations are applied. The startup path does this automatically through `config/migrator.js`.

## Local-only skip flag

For local agent workflows that need the server to boot without running the startup database bootstrap in `init.js`, you can set:

```sh
SKIP_STARTUP_MIGRATIONS=true npm run start:dev
```

This skips the startup call to `migrator({ command: "up", sync: true })`.

Use this only for local, non-deployment tasks such as route, middleware, or UI-adjacent debugging that does not depend on validated database state. In deployment, leave `SKIP_STARTUP_MIGRATIONS` unset or false.

## Non-local startup override

If an environment intentionally runs startup bootstrap against a non-worktree database, set:

```sh
ALLOW_NON_LOCAL_STARTUP_DB_BOOTSTRAP=true npm run start
```

Without that override, `init.js` expects:

- `DB_HOST` to resolve to the local machine (`127.0.0.1`, `localhost`, `::1`, or `0.0.0.0`)
- `DB_PORT` to match the worktree-local port generated by `npm run worktree:bootstrap`
- the target port to be reachable before startup bootstrap begins

This keeps local agents from accidentally running `sync: true` and pending migrations against the wrong database.

## File location

- Migration files live in `migrations/`
- The runner lives in `config/migrator.js`
- The CLI entrypoints live in `scripts/run-migrations.js` and `scripts/new-migration.js`
- Master startup bootstraps the current model graph and applies pending migrations from `init.js` before workers are forked

## Migration shape

Generated files export `up` and `down` functions:

```js
module.exports = {
	async up(queryInterface, sequelize) {},
	async down(queryInterface, sequelize) {},
};
```

`queryInterface` is the primary migration API. `sequelize` is also passed for cases where direct access to the Sequelize instance is useful.

## Template guidance

- Prefer migrations for schema evolution.
- App startup bootstraps the current model graph and applies pending migrations in the master process before workers are started.
- App startup bootstraps the current model graph and applies pending migrations in the master process before workers are started, but only when the DB target passes the startup guard.
- Use `sync: true` only through the existing migrator flow in `config/migrator.js`; do not reintroduce raw `sequelize.sync()` calls in parallel startup paths.
- Use `npm run migrate -- --sync` when you intentionally want to mirror the startup bootstrap path outside the normal server boot flow.
- `SKIP_STARTUP_MIGRATIONS=true` may be used only as a local agent escape hatch when the task intentionally does not require startup DB bootstrap.
- `ALLOW_NON_LOCAL_STARTUP_DB_BOOTSTRAP=true` may be used only in environments that intentionally bootstrap a non-local database, such as deployment or a controlled shared staging environment.
- Keep migrations additive, reviewable, and reversible when practical.

## Hard rules

- Use only the existing migration structure: `migrations/`, `scripts/new-migration.js`, `scripts/run-migrations.js`, `config/migrator.js`, and `init.js`.
- Do not add parallel migration directories, alternate migration CLIs, separate schema-version tables, or a second migration framework unless the repository is explicitly being migrated away from the current Umzug flow.
- Do not bypass the canonical process with hand-run DDL, ad hoc startup scripts, or undocumented one-off database patch files for normal schema evolution.
